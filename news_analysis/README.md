# Анализ новостей: ранжирование, связи и действия

Набор с исследовательским обоснованием: [training_v2](../data/training_v2/README.md).
Для него `fit` и `train_ranker` отвергают отложенные записи; использовать
`bundle/eligible.jsonl` с исходным `dataset_split`. Ссылки на исследования
не являются обученными коэффициентами, финансовыми исходами или экспертным эталоном.

Расчётный Python-модуль поверх `company_context`, Python 3.10+, стандартная библиотека.
Содержит обучаемое ранжирование, расчёт косвенной релевантности по графу и условную
оптимизацию действий. Готовых обученных весов в поставке нет; есть стартовый корпус
с AI-разметкой и сборщик `news_analysis.dataset`. Для независимой оценки нужны люди.
Нет демо, веб-интерфейса или сетевых вызовов.
Синтетические значения используются только в изолированных unit-тестах.

## Граница модуля

Вход: профиль/SQLite задачи 1, структурированные события от парсера, при наличии —
фрагменты аналитики банка от RAG и отдельно предоставленные параметры сценария.
Выход: JSON-карточки с источниками, признаками, оценкой релевантности, условными
направлениями действий, расчётами вариантов и предупреждениями о недостающих данных.

Извлечение событий из текстов, установление фактов, кластеризацию перепечаток и
поиск аналитики выполняют другие компоненты. Этот модуль не объявляет банковской
позицией собственные выводы. `fact_status` — статус, переданный источником/парсером,
а не результат независимой проверки в этом модуле.

В агент можно подключить `analyze_news`, `PaymentGraph.exposure`, `optimize_actions`
как инструменты. `trace` фиксирует шаги расчёта; полный планировщик LLM и повторный
поиск источников остаются ответственностью агентного ядра.

## Python API

```python
from company_context import ContextStore
from news_analysis import analyze_news, LogisticRanker, optimize_actions

# events: список объектов события из контракта ниже.
# model_data: JSON-артефакт, полученный командой train на вашей разметке.
model = LogisticRanker.from_dict(model_data)
with ContextStore(database_path) as store:
    result = analyze_news(store, company_id, events, as_of,
                          model=model, cases=scenario_cases,
                          bank_analytics=bank_excerpts, limit=10)
```

`model=None` включает явно обозначенный `manual_feature_baseline` для подключения
компонентов до разметки. Это новый сравнительный скоринг по признакам пары,
вдохновлённый приоритетами `signals.py`, а не обученная модель и не исходный
алгоритм ранжирования: в исходном модуле такого алгоритма не было.

## 1. Обучаемое ранжирование

Для пары компания–событие извлекаются 20 признаков версии `company_event_v1`:
сочетание ставки с финансированием/депозитом, валютного события со сведениями ФТС,
совпадение ОКВЭД, страны, региона, явно сопоставленного ID, связи группы/физлиц,
доли и покрытие платежей в каждом направлении, давность публикации, спорность фактов
и индикаторы неизвестных значений. Все признаки ограничены диапазоном 0..1.
Точные имена: `features.FEATURE_NAMES`; каждому сопоставлены ссылки на профиль,
граф и источники события. `null` в профиле не означает отсутствие продукта.

Модель: `sigmoid(intercept + sum(weight_i * feature_i))`.
Целевая функция — средняя бинарная log-loss плюс `l2 / 2 * sum(weight_i ** 2)`;
свободный член не штрафуется. Используется градиентный спуск с уменьшением шага
до снижения функции потерь. Коэффициенты общие для компаний. Параметры остановки
и факт сходимости записываются в артефакт; достижение лимита итераций не означает
сходимость. При необходимости увеличьте `--iterations` после проверки отчёта.

Шкала разметки: 0 — не относится; 1 — косвенно; 2 — важно; 3 — требует внимания.
Для обучения 2/3 преобразуются в положительный класс; NDCG использует всю шкалу.
Оценка 0..1 не калибрована как вероятность и не является вероятностью убытка.
`logit_contribution` — произведение признака на коэффициент относительно нуля,
не SHAP, не причинный эффект и не процентные пункты.

### Подготовка и обучение

1. Подготовить JSON-массив событий по контракту ниже.
2. Выгрузить пары с `label=null` для ручной оценки:

```sh
python -m news_analysis prepare-labels --database data/processed/company_context.sqlite --company-ids U_67 U_9250 --events data/processed/news.json --as-of 2026-10-22T18:00:00+03:00 --output data/processed/labels.jsonl
```

3. Люди заполняют `label` и `annotation_reason`. Контекст, признаки и их источники
   уже находятся в строке; не менять признаки при разметке. Включить разные
   компании, косвенные связи и нерелевантные новости той же отрасли. Несколько
   сотен пар — старт эксперимента, а не гарантия качества.
4. Обучить и получить отдельный отчёт:

```sh
python -m news_analysis train --dataset data/processed/labels.jsonl --model-out data/processed/ranker.json --report-out data/processed/ranking_report.json
```

Разделение 60/20/20 выполняется по хронологии **целых кластеров `split_group_id`**
(если поле не задано, используется `event_id`), а не
случайных пар. Все компании и перепечатки одного события попадают в одну часть.
Кластер датируется последней публикацией в нём. L2 выбирается по validation NDCG@5;
затем модель переобучается на train+validation и оценивается на test.
Метки test не участвуют ни в обучении, ни в выборе L2. Для запуска нужно минимум
10 событий и оба класса в обучающей части; для содержательной оценки нужно больше.

`--holdout-companies U_...` полностью исключает выбранные компании из обучения
и подбора L2. Дополнительная оценка проводится на их событиях из test-части.
Отчёт сравнивает модель с `manual_feature_baseline`: Precision@5 и NDCG@5.
Для короткой подборки знаменатель Precision — `min(5, число событий)`;
NDCG группы без релевантных событий равен 0. Оценка относится к кандидатам на входе,
а не к полноте внешнего поиска. Малые/пустые тестовые группы отражаются в счётчиках.

Строка JSONL: `company_id`, `event_id`, `query_id` (компания и момент подборки),
`published_at` с часовым поясом, `feature_version`, `features` со всеми 20 именами,
`label`, `label_origin` (`human`, `ai` или `synthetic`). Для AI обязательны
`annotator`, `rubric_version`, `annotation_reason`. Экспорт добавляет `as_of`,
`annotation_reason`, `annotation_context`. Обучение на непоставленных метках,
одном классе или смеси происхождений меток отклоняется. Synthetic поддержан только
для проверки механики; качество на нём не подтверждает качество на реальных новостях.

[Набор v1](../data/training_v1/README.md) содержит 480 AI-размеченных пар и готовые
признаки. Его `dataset_split` закрепляет части train/validation/test и компании
holdout: обучение сохраняет это разделение и после частичного импорта human-меток.
Для файлов с закреплёнными частями переопределять holdout нельзя. Метрики AI-теста
имеют статус `provisional_ai_agreement`, а не независимой оценки качества.

JSON-артефакт содержит версию признаков, коэффициенты, происхождение меток и SHA-256
обучающего файла в каноническом представлении. Загрузка не использует pickle.
Контекст компаний — предоставленный снимок; для исторической проверки нужны
снимки, доступные на соответствующую дату, чтобы исключить утечку будущих данных.

## 2. Граф

Для каждого направления отдельно:

`matched_share = сумма платежей совпавшим контрагентам / все наблюдаемые платежи направления`.

Совпадение — известный двухзначный ОКВЭД, регион регистрации, страна ФТС или ID с
явно предоставленной привязкой. Один контрагент учитывается один раз даже при
нескольких совпадениях. Читаются все платежи клиента из SQLite, независимо от
`top_n` профиля. Decimal сохраняет точность агрегирования; JSON-доли — float.
Показываются покрытие и номера записей-оснований. Список оснований может усекаться,
итоги — нет. `attribute_coverage_share` означает долю платежей контрагентам,
у которых известен хотя бы один запрошенный атрибут; это не полнота всех атрибутов.
При неполных карточках `matched_share` — нижняя оценка наблюдаемого совпадения.

Связи по группе/общим физлицам проверяются по всем записям; используются как
бинарный признак связи с явно сопоставленной компанией. Владение не утверждается.
Неизвестные контрагенты сохраняются в знаменателе. Отсутствие платежей/нулевой
поток даёт `matched_share=null`. Вектор модели сохраняет индикаторы неизвестности.

Синтетический `U_*` не сопоставляется автоматически с реальной фирмой из текста.
`company_ids` можно передавать только вместе с `entity_mapping_source`.
Граф оценивает значимость события. Он не измеряет ущерб, финансовую зависимость,
вероятность дефолта или действительные роли покупателей/поставщиков.

## 3. Сценарии и подбор действий

Модель работает с одной явно заданной экспозицией за один горизонт:

- `rate_change`: чувствительный к изменению ставки остаток долга/депозита;
  исходное влияние = `sign * exposure_rub * delta_rate * horizon_months / 12`.
- `fx_change`: открытая валютная экспозиция в рублёвом эквиваленте за весь горизонт;
  влияние = `sign * exposure_rub * delta_fx`.
- `commodity_price_change`: объём чувствительных закупок/продаж в рублях за весь
  горизонт; влияние = `sign * exposure_rub * delta_price`.

`exposure_side=cost` даёт sign=+1; `revenue` — sign=-1. Положительное влияние —
дополнительная нагрузка, отрицательное — выгода. Знак не выводится из ОКВЭД/ФТС.
Изменение ключевой ставки нельзя без допущения подставить вместо изменения
ставки конкретного договора. Для валюты нужны встречные потоки и действующая защита;
агрегированные платежи неизвестной валюты нельзя использовать как экспозицию.

Каждое действие покрывает отдельную долю той же экспозиции. Например, разные части
открытого объёма могут иметь разные условия фиксации/защиты, если это реально доступно.
Каталог действий, цены и доступность передаются вызывающей стороной. Автоматических
торговых операций, платежей и заключения договоров модуль не выполняет.

`protected_fraction_i = fraction_i * effectiveness_i * max(0, 1 - lead_time_months_i / horizon_months)`

`остаточное влияние = исходное влияние * (1 - сумма protected_fraction_i)`

`затраты = сумма (фиксированная стоимость при fraction>0 + fraction * переменная стоимость)`

`чистая экономия = исходное влияние - остаточное влияние - затраты`

Поиск меняет **доли действий**, коэффициенты эффекта остаются фиксированными.
При `objective=base` максимизируется чистая экономия основного сценария, что
эквивалентно минимизации остаточного влияния плюс расходов. При `robust` — минимум
чистой экономии среди всех переданных сценариев. Вероятности сценариев не выдумываются.

Ограничения: сумма долей <=1 (нет двойной защиты), доступность и максимальная доля
каждого действия, бюджет расходов, отдельный лимит связанной ликвидности, число
действий и минимальный чистый ROI. Связанная ликвидность не считается расходом;
её альтернативная стоимость должна входить в стоимость действия. Погашение долга,
операционные изменения с взаимозависимостями и синергии требуют отдельной модели
денежных потоков; данная формула не моделирует их автоматически.

Полный перебор объявленной сетки: максимум 100 000 сочетаний и 500 000 пар
«сочетание–сценарий». Максимальная доля включается в сетку даже при неполном шаге.
Нулевое действие всегда рассматривается и выигрывает при отсутствии выгоды.
Есть альтернативы с меньшими затратами/числом действий при сохранении >=90%
максимальной расчётной экономии. `evaluate_plan` проверяет также произвольные доли,
не обязательно лежащие на сетке, и возвращает нарушения ограничений.

Оптимальность относится только к заданной сетке и формуле. Эффективность действий
не обучена на реальной истории. Проверка нескольких шоков не является доверительным
интервалом. Для эмпирической модели нужны история действий, их исполнения, затрат,
исходов и обоснованный способ отделить эффект действий от различий компаний.

### Контракт сценария

Числовые финансовые параметры имеют форму
`{"value": число, "basis": "supplied" или "assumption", "source": "документ/поле/обоснование"}`.
`supplied` означает предоставлено вызывающей стороной, а не подтверждено банком.
Отсутствующий параметр не заменяется нулём. `null` в экспозиции/шоке/параметрах
доступного действия возвращает `needs_parameters` без числовой рекомендации.

| Поле | Содержание |
|---|---|
| `case_id`, `company_id`, `event_id` | Идентификаторы; проверяется привязка к компании и событию |
| `kind` | rate_change / fx_change / commodity_price_change; соответствует типу события |
| `currency`, `exposure_side` | RUB; cost / revenue |
| `horizon_months` | Положительное число месяцев, максимум 120 |
| `exposure_rub` | Неотрицательная экспозиция с basis/source |
| `shocks` | 1–100 объектов `{id, delta}`; delta — параметр с basis/source |
| `base_scenario` | ID основного сценария |
| `objective` | base (по умолчанию) / robust |
| `actions` | Не более 10 действий; пустой список допустим |
| `constraints` | budget_rub, liquidity_limit_rub, max_actions; необязательный min_roi, по умолчанию 0 |

`delta` — доля: +1 п.п. ставки = 0.01; +10% цены/курса = 0.10.
Применяется постоянный шок на всём горизонте и постоянная экспозиция. Изменение
экспозиции во времени, динамика цен и гарантии прогноза не предполагаются.

Действие: `id`, `title`, `available` (обязательно boolean); при доступности также
`max_fraction` (0..1), `step` (>0), `lead_time_months`, `prerequisites` (строка)
и четыре параметра с basis/source:

- `effectiveness`: доля подавляемого шока на защищаемой части, 0..1;
- `fixed_cost_rub`: разовый расход при применении действия;
- `variable_cost_rub`: расход **за весь горизонт при доле 1**, линейно масштабируется;
- `liquidity_required_rub`: объём связанной ликвидности при доле 1.

Затраты должны быть дополнительными относительно базового варианта, включать
применимые комиссии, премии, трудозатраты и упущенную выгоду. Они не масштабируются
повторно по месяцам. Задержка сокращает защиту, но не автоматически расходы.
Текущая версия принимает неотрицательные затраты и не моделирует долговое погашение.

## Контракт события и результат

Каждое событие: обязательные `news_id`, `event_id`, `title`, `published_at` с часовым
поясом, `event_type`, `fact_status` (reported/confirmed/disputed), `sources`.
Типы: rate_change, fx_change, commodity_price_change, trade_restriction,
regional_event, company_event, other. Источник содержит HTTP(S) `url` и `excerpt`.
Необязательно: `event_at`, списки `okved_divisions` (двузначные коды), `countries`,
`regions`, `company_ids`; для последних требуется `entity_mapping_source`.
Сопоставление текста нечувствительно к регистру и ё/е, но не включает геокодер
или справочник синонимов стран: нормализация сущностей — задача парсера.

Перепечатки связывает одинаковый `event_id`. Выбирается самая поздняя доступная
на `as_of` публикация; её признаки и источники сохраняются вместе. Более поздние
публикации исключаются. Противоречивые извлечения разных публикаций автоматически
не разрешаются. Для этого нужны проверка источников и единый event_id на стороне агента.

Аналитика банка: массив `{event_id, source, excerpt}`. Возвращается в `bank_view`
отдельно от `facts` и `model_assessment`. Без неё `bank_view=[]` и предупреждение,
позиция банка не генерируется. `conditional_advice` предлагает направления проверки,
а конкретные доли и стоимость находятся в `scenario.recommendation` при наличии
входных параметров. `self_check` сообщает о пробелах; это проверка контрактов и
полноты данных, не проверка истинности первоисточников.

```sh
python -m news_analysis analyze --database data/processed/company_context.sqlite --company-id U_67 --events data/processed/news.json --as-of 2026-10-22T18:00:00+03:00 --model data/processed/ranker.json --cases data/processed/cases.json --bank-analytics data/processed/bank.json --output data/processed/analysis.json
python -m news_analysis optimize --case data/processed/case.json --output data/processed/actions.json
python -m unittest discover -s tests -v
```

Все входные файлы в примерах должны подготовить соответствующие компоненты проекта.
`--cases`, `--bank-analytics`, `--model` необязательны. Некорректные аргументы CLI
завершаются с кодом 2. Запись поверх входного файла блокируется; SQLite открывается
на чтение. Артефакты следует хранить в уже исключённом из Git `data/processed/`.

## Проверка и основания реализации

Тесты проверяют все исходные сценарии `company_context`, обучение на метках,
сжатие весов регуляризацией, отсутствие влияния test-меток на модель, разбиение
по событиям, сериализацию, полный знаменатель графа, покрытие, направления,
конфликт ФТС, привязку сценария, источники, формулы и оптимум независимым перебором,
ограничения, отсутствие действий при невыгодности, задержки и противоположный знак
эффекта для затрат/выручки. Эти тесты проверяют код, а не качество рекомендаций
на реальном бизнесе.

Из опыта проекта удержания перенесены разделение модели и оптимизатора, фиксированные
коэффициенты при подборе действий, нулевой вариант, чистая экономия после расходов,
ограничения и сравнение сценариев. HR-коэффициенты, данные и обученные веса не переносились.
В этой версии модель действия — объявленная финансовая формула, не переобученная
модель удержания и не причинная модель из корреляций.

Математические ориентиры: [логистическая регрессия и регуляризация](https://scikit-learn.org/stable/modules/linear_model.html#logistic-regression),
[метрики ранжирования](https://catboost.ai/docs/en/concepts/loss-functions-ranking),
[различие прогноза и сценарного расчёта](https://otexts.com/fpp3/regression.html).
Код этих библиотек не скопирован, зависимостей от них нет.
